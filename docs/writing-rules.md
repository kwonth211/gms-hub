# GMS Hub 글쓰기 규칙

사이트에 올라가는 모든 글(공략, 퀘스트 공략, 사냥터 추천, 도구 설명, 안내 문구, 업데이트 소식)에 적용한다.
Claude, Codex, 그 밖의 어떤 에이전트든 글을 쓰거나 고칠 때 이 규칙을 먼저 읽고, 올리기 전에 맨 아래 점검 목록으로 스스로 검토한다.
2026-11-23 사이트 주인이 정했다. 이유: 글이 보고서처럼 둘러대서 사람이 쓴 글로 읽히지 않았다(애드센스 심사 4회 거절, 사유 "콘텐츠 품질").

## 1. 딱 잘라 말한다

게임 하는 사람이 친구에게 알려 주듯이 쓴다. 어디로 가라, 뭘 사라, 몇 방에 잡혀야 한다를 직접 말한다.

| 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| 파퀘나 주니어 레이스를 비교해요 | 파퀘나 주니어 레이스로 넘어가요 |
| 저비용 사냥을 비교할 대표 후보예요 | 돈을 덜 쓰고 사냥하기 좋은 대표 자리예요 |
| 루팡이 한 방인지 확인하세요 | 루팡이 한 방에 잡혀야 해요 |
| 짧게 시험해요 | 잠깐 가 보세요 |
| 표시 레벨은 이동 검토 구간이에요 | 표시된 레벨은 이 사냥터로 옮길 만한 구간이에요 |
| 판매 완료 표시는 관측된 상태예요 | '판매 완료'는 팔린 것으로 확인된 매물에 붙는 표시예요 |
| 힐만으로 효율이 나온다고 가정하지 않기 | 힐만 있으면 효율이 나온다고 믿지 않기 |
| 공식 근거를 다시 확보하기 전까지 제외했어요 | 공식 안내를 다시 확인한 뒤에 넣으려고 지금은 뺐어요 |

## 1-1. 들어온 사람이 찾는 답을 맨 위에 둔다 (2026-11-26)

사이트 주인: "독자들이 원하는 정보가 바로 나올 수 있느냐가 중요해. 들어온 사람의 관점에서 문서를 작성해."

- 이 글을 검색해서 들어온 사람이 무엇을 알고 싶은지 먼저 정한다. 예: "헌터 스킬트리" → 레벨별 스킬 찍는 순서, "커닝 파퀘" → 입장 조건과 단계별 답.
- 첫 화면에 독자의 상황과 그때 할 일을 둔다. 숫자 표는 선택을 빠르게 만드는 데 필요할 때 쓴다. 이야기형 분석에서는 자세한 표와 계산을 뒤로 보내고, 첫 화면을 숫자로 채우지 않는다.
- 많이 찾는 내용부터 순서대로 쓴다. 배경과 설명은 뒤로 보낸다.
- 소제목은 그 칸이 답하는 내용으로 쓴다. ("스킬 이야기" 말고 "레벨별 스킬 찍는 순서")
- 자주 묻는 질문의 답은 첫 문장에서 바로 답한다.
- 분량은 쓸모 있는 답을 더해서 늘린다. 같은 말을 되풀이해서 늘리지 않는다.

## 2. 둘러대는 말을 쓰지 않는다

아래 낱말은 판단을 읽는 사람에게 떠넘기는 말이다. 쓰지 않는다.

- 비교해요, 비교하세요, 비교한 뒤, 견줘 보세요
- 시험해요, 시험하세요, 검토
- 후보, 기준점, 조건부
- 관측, 가정, 근거, 표본 (계산 방법을 설명하는 도구 페이지의 수학 용어는 예외)
- "~일 수 있어요", "달라질 수 있어요"를 버릇처럼 붙이지 않는다. 실제로 경우가 갈릴 때만 쓰고, 어떤 경우에 갈리는지 같이 적는다.
- "~하지 마세요"만 늘어놓지 않는다. 하지 말 것보다 할 것을 먼저 적는다.

모르는 것은 모른다고 한 번만 짧게 쓴다. 예: "76 이후는 아직 사냥 기록이 없어요."

## 2-1. 오래 플레이한 유저의 말투로 쓴다 (2026-11-28)

사이트 주인: "AI 티는 절대 나면 안 되고", "메이플 베테랑 20년차 플레이어로서 글클메에 가이드를 쓰면 돼."

- 말투의 기준은 메이플을 오래 한 유저가 옆에서 알려 주는 해요체다. 뭘 사고, 어디에 돈을 아끼고, 언제 장비를 바꿀지 바로 말한다.
- "이것도 아니고 저것도 아니다", "단순히 X가 아니라 Y다" 같은 대조 문장으로 서론을 채우지 않는다.
- "출처를 확인하세요", "직접 검증하세요", "각자 판단하세요"처럼 작성자가 할 일을 독자에게 넘기지 않는다. 자료와 계산은 작성 과정에서 확인하고, 본문에는 결론과 그 선택이 필요한 상황을 쓴다.
- 추천 뒤에는 게임에서 생기는 차이를 붙인다. 돈이 얼마나 드는지, 몇 방에 잡히는지, 다음 장비까지 얼마나 쓰는지처럼 실제 선택에 필요한 내용을 적는다.
- 베테랑 말투는 문체 기준이다. 작성자의 플레이 연차, 캐릭터, 직접 사냥하거나 거래했다는 경험은 실제 기록이 있을 때만 쓴다. 시세 집계와 계산 결과를 직접 플레이한 일화로 바꾸지 않는다.
- 예산·직업·장비에 따라 답이 갈리면 각 상황에서 할 일을 바로 적는다. 숫자가 없으면 지어내지 않는다.

## 2-2. DB에서 찾은 인사이트를 플레이 이야기로 푼다 (2026-11-28)

사이트 주인: "우리 디비 데이터에 인사이트가 있으니까 그게 전문가인 거야. 너무 수치적으로 이야기하기보단 스토리텔링 형식으로 경험과 독창성이 있는 게 좋을 것 같아."

- 독자가 게임에서 마주치는 구체적인 순간으로 시작한다. 첫 주문서가 실패했을 때, 새 표창을 살 돈을 모았을 때, 사냥하고 돌아왔는데 메소가 남지 않을 때처럼 선택이 필요한 장면을 쓴다.
- 상황 → 끌리는 선택 → DB에서 드러난 놓치기 쉬운 차이 → 다음에 할 행동으로 이야기를 잇는다. 모든 글에 같은 소제목이나 문장 틀을 반복하지 않는다.
- 전문성은 숫자를 많이 나열하는 데서 나오지 않는다. 왜 그 돈을 여기서 아끼고 다른 장비에 써야 하는지 설명한다. 본문 숫자는 선택을 바꾸는 것만 남긴다.
- 자세한 집계표, 확률표, 수식과 집계 방법은 글 뒤의 펼쳐 보는 자료에 둔다. 가격의 날짜와 중요한 적용 조건은 본문에서 바로 알 수 있게 쓴다.
- 경험이 느껴지는 문체로 쓰되, 없는 플레이 경험이나 유저 사례를 만들지 않는다. 일반적인 상황은 "~하려고 상점을 보고 있다면"처럼 독자의 상황으로 쓴다. 실제 기록으로 확인한 일은 기록이 보여 주는 범위 안에서 말한다.
- 이야기만 길게 늘이지 않는다. 첫 화면에서 고민에 대한 답을 주고, 마지막에는 독자가 이어서 할 행동과 관련 기능을 연결한다.

## 3. 쓸데없는 설명을 넣지 않는다

- 읽는 사람이 이미 아는 것, 글이 어떻게 만들어졌는지, 무엇을 뺐는지, 왜 조심스러운지를 설명하지 않는다.
- 출처 이름, 자료 비교, "편집 제안", "보장하지 않음" 같은 면책 문구를 본문에 넣지 않는다.
- 한 문단은 2~4문장. 한 문장에 한 가지만 말한다.

## 4. 그대로 두는 것

- 숫자, 레벨, 확률, 가격, 아이템·몬스터·맵 이름, 링크, 표 구조.
- 실제 정보가 담긴 문장. 예: "소울 애로우를 켜면 화살이 들지 않아요."
- 말투는 해요체. 아이템 드롭은 "드랍"으로 쓴다.

## 5. 올리기 전 점검

1. 2번의 낱말이 새로 들어가지 않았는가. `node --test tests/voice.test.mjs`가 파일별로 세어서, 전보다 늘면 실패한다.
2. 문장마다 "그래서 뭘 하라는 건데?"에 답이 있는가.
3. 지워도 뜻이 안 바뀌는 문장이 남아 있지 않은가.
4. 고치기 전과 숫자·링크·이름이 같은가.
5. 영어판도 같은 식으로 썼는가. "compare, candidate, consider, observed, benchmark, verify"는 같은 테스트가 세고, "test / trial / may / assume"도 둘러대는 뜻이면 쓰지 않는다. 대신 "go to", "move to", "you need", "stay while"로 쓴다. (게임의 "test server", 전직 시험 "trial", 확률 계산의 "assumes"는 그대로 둔다.)
6. 독자에게 자료 확인을 떠넘기거나, 실제 기록에 없는 플레이 경험을 만들어 넣지 않았는가.
7. DB 수치를 늘어놓는 대신 독자의 선택이 달라지는 이유를 설명했는가. 장면만 붙인 서론 뒤에 같은 숫자 보고서를 반복하지 않았는가.

`tests/voice-baseline.json`의 숫자는 아직 못 고친 글에 남아 있는 개수다. 글을 고치면 그 숫자를 낮춘다. 높이지 않는다.
